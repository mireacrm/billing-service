# Сервис биллинга

Отвечает за выставление счетов по завершённым записям, фиксацию оплаты
и расчёт комиссии специалистов.

Счёт создаётся асинхронно после получения события `appointment.completed`.
Для получения стоимости и других данных завершённой записи сервис обращается
по gRPC к `booking-service`.

После оплаты Billing Service запрашивает начисление баллов у `client-service`
и публикует событие `invoice.paid`.

## Возможности

Сервис предоставляет следующие методы:

| Метод | Назначение |
|---|---|
| `GET /invoices/{invoice_id}` | Получение счёта |
| `POST /invoices/{invoice_id}/pay` | Фиксация оплаты |
| `GET /branches/{branch_id}/invoices` | Получение счетов филиала |
| `GET /employees/{employee_id}/commission` | Расчёт комиссии специалиста за период |

При получении счетов филиала можно использовать параметры `status` и `limit`.
Для расчёта комиссии период задаётся параметрами `from` и `to`.

## Обработка завершённой записи

Billing Service подписан на событие:

```text
appointment.completed
```

После получения события сервис:

1. запрашивает детали записи у `booking-service` по gRPC;
2. получает филиал, клиента, специалиста и зафиксированную цену;
3. создаёт счёт со статусом `issued`;
4. рассчитывает комиссию специалиста;
5. публикует событие `invoice.issued`.

Комиссия составляет 40% от суммы счёта, но учитывается в отчётах только после
фактической оплаты.

## Оплата счёта

При выполнении запроса:

```http
POST /invoices/{invoice_id}/pay
```

сервис изменяет статус счёта на `paid`, запрашивает начисление баллов
у `client-service` и публикует событие `invoice.paid`.

Оплатить можно только счёт со статусом `issued`. Повторная оплата возвращает
ошибку конфликта.

## Доменные события

| Направление | Событие | Назначение |
|---|---|---|
| Входящее | `appointment.completed` | Создание счёта после завершения записи |
| Исходящее | `invoice.issued` | Уведомление о выставлении счёта |
| Исходящее | `invoice.paid` | Уведомление об оплате счёта |

## Хранение данных

Сервис использует отдельную базу PostgreSQL `billing_db`.

Основные таблицы:

- `invoices` — счета, суммы, статусы и комиссии;
- `processed_events` — идентификаторы обработанных событий.

Уникальность `appointment_id` обеспечивает правило «одна запись — один счёт».
Таблица `processed_events` реализует паттерн Inbox и защищает сервис от
повторной обработки событий RabbitMQ.

Одновременная оплата защищена условным обновлением записи в PostgreSQL:
статус изменяется только тогда, когда счёт ещё находится в состоянии `issued`.

## Взаимодействие с другими сервисами

| Сервис | Протокол | Назначение |
|---|---|---|
| `booking-service` | gRPC | Получение данных завершённой записи |
| `client-service` | gRPC | Начисление баллов после оплаты |
| RabbitMQ | AMQP | Получение и публикация доменных событий |

Billing Service не обращается напрямую к базам данных соседних сервисов.

## Служебные методы

| Метод | Назначение |
|---|---|
| `GET /healthz` | Проверка работы процесса |
| `GET /readyz` | Проверка готовности и доступности зависимостей |
| `GET /metrics` | Метрики Prometheus |


## Зависимости

| Пакет | Роль |
|---|---|
| [`mirea-contracts`](https://github.com/mireacrm/contracts-py) | сообщения и стабы gRPC |
| [`mireacrm-common`](https://github.com/mireacrm/py-common) | настройки, метрики, трасса, ошибки, база, события, gRPC |

Оба приезжают из своих репозиториев по версии из `pyproject.toml`.
Версию контрактов называет сервис, а не обвяз: два прямых URL одного
пакета pip считает конфликтом.

## Локально

```
pip install -e ".[dev]"
python -m pytest tests/unit -q
python -m pytest tests/integration -q   # нужен Postgres
docker build -t billing-service .
```

Систему целиком поднимает [`mireacrm/deploy`](https://github.com/mireacrm/deploy).
